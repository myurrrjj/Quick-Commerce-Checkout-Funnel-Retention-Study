# Methodology

This document explains how the dataset is built, how each metric is defined, and the limits of the study.

## 1. Data source

The dataset is simulated. It is generated by `python/gen_data.py` with a fixed random seed of 42, so every run produces the same numbers. No real user data is used anywhere in this repo.

The generator produces 11,700 users and 12,840 sessions over a 61 day window from 1 August 2026 to 30 September 2026. Each session is simulated through a four stage funnel with probabilities that depend on user type, channel, device, city tier and two checkout attributes.

## 2. Why simulate

The goal of this repo is to demonstrate an end to end product analytics workflow: generate or ingest data, model it in SQL, analyse it in Python, chart it, and turn it into product decisions. Simulated data lets the whole pipeline run from a clean clone with no external dependencies, and lets the drop off drivers be controlled so the analysis can be validated.

The trade off is that the numbers are not evidence about any real company. They are a worked example of the method. The generation probabilities encode the hypotheses being tested, so a reader should treat the findings as a demonstration of how to measure these effects, not as proof that they exist.

## 3. Tables

**users**: one row per user. Fields are user_id, acq_channel, device, city_tier, signup_date.

**sessions**: one row per shopping session. Fields include the four funnel flags, plus cart_value, delivery_fee, fee_stage, addr_steps, payment_method.

**events**: the raw event stream in long form. One row per event, ordered by session and time. Event types are item_view, add_to_cart, checkout_start, select_address, payment_attempt, payment_failed, payment_success.

**orders**: one row per completed order. Fields are order_id, user_id, session_id, order_ts, amount, delivery_fee, payment_method, status.

## 4. Funnel definition

The funnel has four stages, defined by flags on the sessions table.

| Stage | Flag | Event anchor |
| --- | --- | --- |
| Item discovery | reached_view | item_view |
| Cart creation | reached_cart | add_to_cart |
| Address selection | reached_addr | select_address |
| Payment done | reached_pay | payment_success |

Conversion at a stage is the count of sessions reaching that stage divided by sessions reaching the previous stage. The cart to payment drop is the count at cart minus the count at payment, divided by the count at cart.

## 5. User type

A session is first time if `is_new = 1`, which means the user has not ordered before. Repeat sessions are all others. Every user has exactly one first time session, and repeat sessions are only generated for users whose first session converted, which mirrors real behaviour.

## 6. Checkout attributes

**fee_stage** is `cart` if the delivery fee was shown at the cart, and `payment` if it was first shown at the payment step. This is the variable behind the fee disclosure finding.

**addr_steps** is the number of steps the user went through to enter an address, from 1 to 4. This is the variable behind the address finding.

## 7. Retention definition

A buyer is any user with at least one order. The first order date defines the cohort week. A user is a repeat buyer if they have two or more orders.

The 30 day repeat rate is the share of buyers whose second order landed within 30 days of their first order. The second order gap is used rather than the last order gap, so that a user who orders twice early and once late is still counted as a repeat within 30 days.

The retention curve plots the share of all buyers whose second order fell within day 1, 3, 7, 14, 21 and 30. Buyers who never repeat are counted in the denominator for every point, so the curve is a true cumulative repeat rate and rises to the overall 30 day repeat figure.

## 8. Known limits

**Censoring in late cohorts.** The last two cohort weeks show low repeat rates because those users have had less time to place a second order before the data window ends. This is right censoring and is expected. Do not read the last cohort as a real decline in retention.

**Simulated correlations.** Because the fee and address effects are built into the generator, the observed effect sizes match the assumptions behind them. In real data these effects would need to be established with an experiment.

**No seasonality or promotions.** The generator does not model festivals, sales or price changes, so the series is smooth by construction.

**Single market.** All amounts are in rupees and the payment mix reflects an India first quick commerce setting, with UPI as the leading method.

## 9. Tools

- Python 3.12 with pandas and numpy for generation and analysis.
- matplotlib for charts.
- SQLite for the SQL layer. The SQL uses window functions and runs unchanged on any modern warehouse.

## 10. Reproducing the results

```bash
pip install -r requirements.txt
python python/run_all.py
```

This writes the four CSVs into `data/`, the analysis CSVs into `outputs/`, and the charts into `outputs/charts/`.
